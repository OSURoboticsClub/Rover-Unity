# Unity UDP ROS Bridge

This documentation was generated by Copilot and may contain errors.

This package provides a small ROS 2 bridge for sending JSON payloads between Unity and ROS over UDP.

The package contains three main ROS nodes:

- `udp_bridge_pub` — receives JSON over UDP and publishes it onto a ROS topic.
- `udp_bridge_sub` — subscribes to a ROS topic and sends the resulting message back to Unity over UDP.
- `udp_bridge_srv` — sends a ROS service request and receives the service response over UDP.

A fourth helper, `ActionBridge.py`, is a separate TCP-based action bridge and is not part of the UDP publish/subscribe/service flow.

## Launch

From the workspace root, source your ROS environment and launch the bridge package:

```bash
source /opt/ros/humble/setup.bash
source /home/nolan/source/Rover-Unity/unity_udp_ros_bridge/install/setup.bash
ros2 launch unity_udp_ros_bridge udp_bridge_launch.py
```

The launch file starts all three nodes:

- `udp_bridge_pub`
- `udp_bridge_sub`
- `udp_bridge_srv`

## Port map

The current bridge implementation uses these UDP ports on `127.0.0.1`:

- `65434` — input for `udp_bridge_pub` (Unity -> ROS publish)
- `65435` — output from `udp_bridge_sub` (ROS topic -> Unity)
- `65436` — input for `udp_bridge_sub` configuration (Unity -> ROS subscribe setup)
- `65437` — input for `udp_bridge_srv` (Unity -> ROS service request)
- `65438` — output from `udp_bridge_srv` (ROS service response -> Unity)

> Important: the code binds these sockets to `127.0.0.1`. That means the bridge is currently loopback-only unless the source code is changed to use a non-loopback host.

## 1. Publishing from Unity into ROS

Use `udp_bridge_pub` when Unity wants to publish a ROS message.

### Incoming UDP payload

```json
{
  "topic": "/chatter",
  "msgType": "std_msgs/msg/String",
  "data": {
    "data": "Hello from Unity"
  }
}
```

### Notes

- `topic` is the ROS topic name.
- `msgType` must be a ROS interface type string, such as `std_msgs/msg/String`.
- `data` is the message payload.
- The bridge creates the publisher lazily the first time it sees a topic.

### Example sender

The repository includes a quick test script at `unity_udp_ros_bridge/unity_udp_ros_bridge/test_udp.py` that can be used as a minimal sender.

## 2. Subscribing from ROS into Unity

Use `udp_bridge_sub` when Unity wants to tell ROS which ROS topic to subscribe to and then receive updates back over UDP.

### Configuration payload sent to port `65436`

```text
topic_name;std_msgs/msg/String
```

For example:

```text
/chatter;std_msgs/msg/String
```

### What happens next

- The node creates a ROS subscriber for that topic and message type.
- Each new ROS message is serialized into a JSON payload and sent to Unity on port `65435`.

### Output payload format

```json
{
  "topic": "/chatter",
  "msgType": "std_msgs/msg/String",
  "data": {
    "data": "Hello from ROS"
  }
}
```

### Rate limiting

The node currently limits outgoing updates to about `30 Hz` per topic.

## 3. Calling services from Unity

Use `udp_bridge_srv` when Unity needs to invoke a ROS 2 service.

### Request payload sent to port `65437`

```json
{
  "service": "/set_bool",
  "srvType": "std_srvs/srv/SetBool",
  "request": {
    "data": true
  }
}
```

### How the bridge responds

The service response is returned to Unity over UDP on port `65438`.

Example response:

```json
{
  "service": "/set_bool",
  "response": {
    "success": true,
    "message": ""
  }
}
```

If the service call fails, the bridge returns an error payload with the error message in the `response` field.

## 6. Unity C# integration

The Unity-side wrapper for this bridge is implemented in [Assets/Control Interface App/UdpController.cs](Assets/Control Interface App/UdpController.cs). It exposes the bridge through a singleton-style `UdpController.inst` object.

### Key methods

- `ConfigureSubscription(topic, msgType)`
  - Sends a subscription request to the ROS bridge on port `65436`.
  - Example:

```csharp
UdpController.inst.ConfigureSubscription("joint_states", "sensor_msgs/msg/JointState");
```

- `PublishMessage(string message)`
  - Sends a JSON publish payload to the bridge on port `65434`.
  - Example:

```csharp
var msg = JObject.Parse(driveMessageJson.text);
msg["topic"] = "cmd_vel";
msg["data"]["angular"]["z"] = rightJoy.x * driveSpeedSlider.value * -1;
msg["data"]["linear"]["x"] = leftJoy.y * driveSpeedSlider.value;
UdpController.inst.PublishMessage(msg.ToString());
```

- `PublishClientReq(string message)`
  - Sends a service request to the bridge on port `65437` and waits for the matching response on `65438`.
  - Example:

```csharp
var msg = JObject.Parse(testServiceJson.text);
msg["service"] = "test_srv";
msg["request"]["data"] = true;
JObject response = await UdpController.inst.PublishClientReq(msg.ToString());
```

- `GetLatestMessage(topic)`
  - Returns the most recent subscription payload received from ROS.

- `GetLatestServiceResponse(serviceKey)`
  - Returns the most recent service response by service name.

### Minimal Unity usage pattern

1. Make sure the `UdpController` component exists in the scene and is initialized.
2. Call `ConfigureSubscription(...)` for topics you want to receive.
3. Call `PublishMessage(...)` with a JSON string containing `topic`, `msgType`, and `data`.
4. Call `PublishClientReq(...)` for service requests and await the returned `JObject` response.

### JSON format reference

The Unity wrapper passes ROS data as JSON strings. The bridge expects the following shapes.

#### Topic publish request

Used by `PublishMessage(...)` to publish a ROS message from Unity into ROS.

```json
{
  "topic": "cmd_vel",
  "msgType": "geometry_msgs/msg/Twist",
  "data": {
    "linear": {
      "x": 0.5,
      "y": 0.0,
      "z": 0.0
    },
    "angular": {
      "x": 0.0,
      "y": 0.0,
      "z": 0.2
    }
  }
}
```

Important fields:
- `topic`: ROS topic name.
- `msgType`: full ROS type path, for example `std_msgs/msg/String` or `geometry_msgs/msg/Twist`.
- `data`: nested object that matches the ROS message schema.

#### Topic subscription registration

Used by `ConfigureSubscription(topic, msgType)`.

This is not JSON. The controller sends a plain string in the form:

```text
topic_name;message_type
```

Example:

```text
/joint_states;sensor_msgs/msg/JointState
```

#### Topic update payload returned from ROS

Incoming topic data received by the controller is shaped like:

```json
{
  "topic": "/joint_states",
  "msgType": "sensor_msgs/msg/JointState",
  "data": {
    "header": {
      "stamp": {
        "sec": 0,
        "nanosec": 0
      },
      "frame_id": ""
    },
    "name": ["joint1", "joint2"],
    "position": [0.0, 0.0],
    "velocity": [0.0, 0.0],
    "effort": [0.0, 0.0]
  }
}
```

#### Service request payload

Used by `PublishClientReq(...)` for a ROS service call.

```json
{
  "service": "/set_bool",
  "srvType": "std_srvs/srv/SetBool",
  "request": {
    "data": true
  }
}
```

Important fields:
- `service`: ROS service name.
- `srvType`: ROS service type, for example `std_srvs/srv/SetBool`.
- `request`: payload that matches the request schema for that service.

#### Service response payload

Returned by the ROS bridge and observed via `WaitForServiceResponse(...)` or `GetLatestServiceResponse(...)`.

```json
{
  "service": "/set_bool",
  "response": {
    "success": true,
    "message": ""
  }
}
```

#### Notes about field structure

- `topic` and `msgType` are always present in publish/update messages.
- `service` and `srvType` are always present in service requests.
- The nested `data` or `request` object should mirror the actual ROS message/service schema exactly.
- For arrays, use JSON arrays, not C# arrays directly; the controller serializes them into `JObject`/`JArray` form before sending.

### `UdpController` method reference

The Unity-side bridge wrapper lives in [Assets/Control Interface App/UdpController.cs](Assets/Control Interface App/UdpController.cs). The methods below are the ones the rest of the project uses.

#### `Reconnect()`
- Access: public
- Parameters: none
- Return type: `void`
- Qualitative role: Re-establishes the Unity-side ROS communication session after the connection has been lost or the controller has been reinitialized. In practice this means “start talking to the ROS bridge again” rather than a high-level ROS operation.

#### `WaitForServiceResponse(string serviceKey, int maxAttempts = 50, float delayBetweenAttempts = 0.1f)`
- Access: public
- Parameters:
  - `serviceKey` — the logical name of the service request being awaited.
  - `maxAttempts` — how many times Unity should check for the eventual response before giving up.
  - `delayBetweenAttempts` — pause between checks.
- Return type: `async UniTask<JObject>`
- Qualitative role: Represents the Unity-side “call-and-wait” model for ROS services. After Unity has sent a service request, this method blocks the coroutine until the response arrives and is cached by the controller, abstracting away the fact that the response is being delivered by the UDP bridge underneath.
- Return data: the service response payload as a `JObject`. If nothing arrives in time, it returns an empty object and logs a timeout warning.

#### `ConfigureSubscription(string topic, string msgType)`
- Access: public
- Parameters:
  - `topic` — the ROS topic that Unity wants to receive updates from.
  - `msgType` — the ROS message type associated with that stream.
- Return type: `void`
- Qualitative role: Tells the ROS bridge “I want to subscribe to this topic and receive future messages in this format.” From Unity’s point of view, it is setting up a one-way ROS data stream into the game.
- Result: once configured, the controller keeps the latest received topic payload in memory so C# scripts can query it later with `GetLatestMessage(topic)`.

#### `PublishMessage(string message)`
- Access: public
- Parameters:
  - `message` — a ROS publish command serialized as JSON, usually carrying a target topic name and field data.
- Return type: `void`
- Qualitative role: This is Unity’s “send a ROS topic command” entry point. It is used for control-style traffic such as drive commands, joystick input, or other outgoing topic publications.
- Result: the message is published into the specified ROS topic through the bridge, without requiring the Unity script to know any low-level networking details.

#### `PublishClientReq(string message, string serviceKey = null)`
- Access: public
- Parameters:
  - `message` — a JSON request describing a ROS service call.
  - `serviceKey` — optional name used to match the later response to the original request.
- Return type: `async UniTask<JObject>`
- Qualitative role: This is the Unity-side service invocation method. It abstracts the ROS service call as “send the request, then await a response object.” The controller handles the internal mapping from request to eventual response payload.
- Result: the method returns the service reply as a `JObject` once the ROS side completes the request.

#### `GetLatestMessage(string topic)`
- Access: public
- Parameters:
  - `topic` — the ROS topic whose last received payload should be returned.
- Return type: `JObject`
- Qualitative role: Acts as the Unity-side “read the latest ROS topic value” accessor. It is the simple consumer API for any topic that has already been registered with `ConfigureSubscription(...)`.
- Return data: the most recently received topic message payload for that topic, or `null` if nothing has arrived yet.

#### `GetLatestServiceResponse(string serviceKey)`
- Access: public
- Parameters:
  - `serviceKey` — the logical service identifier whose reply should be read back.
- Return type: `JObject`
- Qualitative role: Provides the Unity-side “read the latest service reply” accessor. Unlike `PublishClientReq(...)`, this does not initiate a new request; it simply reads the cached response that was already received from ROS.
- Return data: the latest cached response object, or `null` if no response has been stored for that service key.

#### Internal lifecycle methods

- `Start()`
  - Access: private
  - Parameters: none
  - Return type: `void`
  - Qualitative role: Initializes the Unity-side ROS communication session by opening the sockets used to send requests and receive topic/service updates. This is the internal setup step that makes the higher-level methods above usable.

- `Update()`
  - Access: private
  - Parameters: none
  - Return type: `void`
  - Qualitative role: Continuously drains incoming ROS traffic into the local cache. In ROS terms, this is the Unity-side event loop that keeps topic values and service replies fresh for later consumption.

- `OnDestroy()`
  - Access: private
  - Parameters: none
  - Return type: `void`
  - Qualitative role: Tears down the Unity-side ROS session cleanly when the object is destroyed.

- `OnApplicationPause(bool pauseStatus)`
  - Access: private
  - Parameters:
    - `pauseStatus` — whether the Unity application is pausing.
  - Return type: `void`
  - Qualitative role: Handles transient loss of connectivity while the game pauses, so later Unity code can reconnect to the ROS bridge cleanly.

## 7. Caveats

- The bridge currently expects `127.0.0.1` and will not automatically accept remote network traffic.
- The subscriber setup format is a semicolon-delimited string, not JSON.
- Message field names must match the ROS message schema exactly.
- `data` in publish requests should be nested exactly as the ROS message expects.
